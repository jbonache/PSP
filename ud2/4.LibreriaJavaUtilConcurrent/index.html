    4. La biblioteca java.util.concurrent

    Des dels inicis de Java la programació multifil ha sigut un dels aspectes fonamentals del llenguatge, amb la interfície Runnable i la classe Thread com a nucli.

    Des de Java 5, a més tenim a la nostra disposició la llibreria java.util.concurrent, que ofereix un conjunt de classes i interfícies orientades a gestionar la programació concurrent d'una forma més senzilla i òptima.

    En aquest apartat veurem una xicoteta introducció a aquesta llibreria. Concretament, veurem la interfície Callable, molt similar a Runnable, però que ens permet utilitzar valors de retorn.

    D'altra banda, l'API ExecutorService ens permetrà separar les tasques de creació de threads, la seua execució i la seua administració, encapsulant la funcionalitat i millorant el rendiment.

    I finalment, veurem la interfície BlockingQueue, que permet gestionar cues de manera que els seus accessos puguen ser bloquejants, la qual cosa ens serà de gran utilitat per a abordar els diferents problemes de sincronització i coordinació, com per exemple el del productor-consumidor, sense la necessitat d'utilitzar monitors.

    La llibreria java.util.concurrent

    La llibreria java.util.concurrent ofereix un conjunt molt ampli de classes i interfícies orientades a gestionar la programació concurrent d'una forma més senzilla i òptima.

    Entre totes elles, es troben l'API ExecutorService i la interfície Callable. La primera s'encarrega de separar les tasques de creació de threads, la seua execució i la seua administració, encapsulant la funcionalitat i millorant el rendiment, mentre que la interfície Callable ens resol el problema dels threads amb els valors de retorn.

    D'altra banda, la llibreria també presenta la interfície BlockingQueue i diverses classes que la implementen amb diferents estructures de dades, amb la característica comuna que els accessos poden arribar a ser bloquejants si la llista està buida o ha arribat al topall de la seua capacitat. Això ens serà de gran utilitat per a abordar diferents problemes de sincronització sense la necessitat d'utilitzar monitors en l'accés a objectes compartits.

    La interfície Callable

    La interfície Callable és una versió millorada de la interfície Runnable introduïda a Java 5, que permet retornar un valor en finalitzar la seua execució.

    Quan utilitzem Runnable, disposem d'un mètode run() que no retorna cap valor. En canvi, Callable<T> proporciona el mètode call(), que retorna un valor de tipus T i pot llançar excepcions.

    En els exemples d'aquest apartat utilitzarem SWAPI (The Star Wars API) com a font de dades. És una API REST oberta que permet consultar informació de l'univers de Star Wars mitjançant peticions HTTP. No requereix autenticació i retorna les dades en format JSON.

    La URL base de l'API és:

    https://swapi.dev/api/

    Per exemple, aquesta petició:

    https://swapi.dev/api/people/1/

    retorna informació sobre el personatge amb identificador 1, Luke Skywalker.

    SWAPI disposa, entre altres, dels recursos people, films, planets, species, starships i vehicles. També permet fer cerques mitjançant el paràmetre search.

    Important: en aquest tema no ens interessa tant el contingut concret de les dades de Star Wars com el fet que el nostre programa haja de fer una petició HTTP i esperar una resposta. Aquesta espera d'entrada/eixida és un bon exemple per entendre per què té sentit utilitzar tasques asíncrones.

    Preparació: una classe per consultar SWAPI

    Abans de començar amb Callable, crearem una xicoteta classe auxiliar que encapsule una petició HTTP.

    Java disposa, des de Java 11, de les classes HttpClient, HttpRequest i HttpResponse en el paquet java.net.http.

    El mètode get de la classe SwapiClient rep una URL i retorna el JSON rebut en forma de String:

    import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class SwapiClient {

    private static final HttpClient CLIENT =
            HttpClient.newHttpClient();

    public static String get(String url) throws Exception {

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create(url))
                .GET()
                .build();

        HttpResponse<String> response =
                CLIENT.send(
                        request,
                        HttpResponse.BodyHandlers.ofString()
                );

        if (response.statusCode() != 200) {
            throw new RuntimeException(
                    "Error HTTP: " + response.statusCode()
            );
        }

        return response.body();
    }
}

    Aquesta classe no utilitza encara cap mecanisme de concurrència. Simplement ens permet fer una consulta a SWAPI.

    Per exemple:

    public class ExempleSwapi {

    public static void main(String[] args) throws Exception {

        String resposta = SwapiClient.get(
                "https://swapi.dev/api/people/1/"
        );

        System.out.println(resposta);
    }
}

    Un primer problema: volem retornar el nom del personatge

    Suposem ara que volem crear una tasca que consulte un personatge de SWAPI i ens retorne el seu nom.

    Una primera versió podria retornar tot el JSON:

    import java.util.concurrent.Callable;

public class ConsultaPersonatge
        implements Callable<String> {

    private final int id;

    public ConsultaPersonatge(int id) {
        this.id = id;
    }

    @Override
    public String call() throws Exception {

        return SwapiClient.get(
                "https://swapi.dev/api/people/" + id + "/"
        );
    }
}

    En aquest exemple, Callable<String> ens indica que la tasca retornarà un String.

    Podem executar call() directament:

    Callable<String> consulta =
        new ConsultaPersonatge(1);

String resultat = consulta.call();

System.out.println(resultat);

    Però això no és una execució asíncrona. El fil principal executa call() i espera que la petició HTTP acabe.

    Important: Callable ens permet definir una tasca que retorna un resultat, però per si sola no decideix en quin fil ni que s'executarà de manera asíncrona. Necedssitarem a l'amic FutureTask.

    FutureTask

    Una primera manera d'executar un Callable de manera asíncrona és utilitzar FutureTask.

    FutureTask<T> implementa RunnableFuture<T>, per la qual cosa podem crear un Thread i passar-li la tasca.

    Partim de la mateixa consulta:

    Callable<String> consulta =
        new ConsultaPersonatge(1);

FutureTask<String> futureTask =
        new FutureTask<>(consulta);

    Ara podem crear i iniciar un fil:

    Thread fil = new Thread(futureTask);

fil.start();

    El fil principal pot continuar executant altres instruccions mentre la consulta està en curs:

    System.out.println("Consulta iniciada");
System.out.println("El programa principal continua...");

    Quan necessitem el resultat, utilitzem get():

    String resultat = futureTask.get();

System.out.println(resultat);

    El mètode get() espera si la tasca encara no ha acabat.

    Podem representar el que està passant així:

    Fil principal                  Fil de consulta
     │                                │
     │ inicia FutureTask              │
     ├───────────────────────────────►│
     │                                │
     │ continua treballant            │
     │                                │
     │                                ├── GET /people/1/
     │                                │
     │                                │    SWAPI
     │                                │
     │                                ◄── resposta JSON
     │                                │
     │◄────── futureTask.get() ───────┤
     │
     ▼
processa el resultat

    Exemple complet amb FutureTask

    import java.util.concurrent.Callable;
import java.util.concurrent.FutureTask;

public class ExempleFutureTask {

    public static void main(String[] args)
            throws Exception {

        Callable<String> consulta =
                new ConsultaPersonatge(1);

        FutureTask<String> futureTask =
                new FutureTask<>(consulta);

        Thread fil = new Thread(futureTask);
        fil.start();

        System.out.println(
                "La consulta s'està executant..."
        );

        String resultat = futureTask.get();

        System.out.println(
                "Resposta rebuda:"
        );
        System.out.println(resultat);
    }
}

    Idea important: FutureTask ens permet associar una tasca (Callable) amb un resultat que podrem recuperar posteriorment.

    L'API ExecutorService

    Encara que FutureTask és útil per entendre el mecanisme, no és habitual crear manualment un Thread per cada tasca.

    Quan tenim moltes tasques, podem utilitzar ExecutorService.

    ExecutorService proporciona un conjunt de fils que poden anar executant les tasques que li enviem. D'aquesta manera, separem la definició de les tasques de la gestió dels fils.

    Per exemple, podem crear un executor amb quatre fils:

    ExecutorService executor =
        Executors.newFixedThreadPool(4);

    Ara podem enviar-li la nostra tasca ConsultaPersonatge.

    Future<String> resultat =
        executor.submit(
                new ConsultaPersonatge(1)
        );

    El mètode submit() retorna un objecte Future<String> que representa el resultat futur de la tasca.

    Podem recuperar-lo amb:

    System.out.println(resultat.get());

    I, quan ja no necessitem l'executor:

    executor.shutdown();

    Exemple complet

    import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class ExempleExecutorService {

    public static void main(String[] args)
            throws Exception {

        ExecutorService executor =
                Executors.newFixedThreadPool(4);

        Future<String> resultat =
                executor.submit(
                        new ConsultaPersonatge(1)
                );

        System.out.println(
                "La consulta s'està executant..."
        );

        System.out.println(
                resultat.get()
        );

        executor.shutdown();
    }
}

    Future

    La interfície Future representa el resultat d'una operació asíncrona.

    Quan fem:

    Future<String> resultat =
        executor.submit(tasca);

    no tenim encara necessàriament el String. Tenim un objecte que ens permet controlar i consultar el resultat que obtindrem quan la tasca acabe.

    Podem utilitzar, entre altres, els mètodes següents:

    Mètode Descripció
    isDone() Indica si la tasca ha acabat.
    get() Espera fins que la tasca acabe i retorna el resultat.
    get(long, TimeUnit) Espera com a màxim el temps indicat.
    cancel(boolean) Intenta cancel·lar la tasca.
    isCancelled() Indica si la tasca ha sigut cancel·lada.

    isDone()

    Podem comprovar si una consulta ja ha acabat:

    Future<String> resultat =
        executor.submit(
                new ConsultaPersonatge(1)
        );

if (resultat.isDone()) {
    System.out.println("La consulta ha acabat");
} else {
    System.out.println(
            "La consulta encara està en curs"
    );
}

    És important recordar que el resultat de isDone() depén del moment en què el consultem.

    get()

    Quan necessitem el resultat:

    String dades = resultat.get();

System.out.println(dades);

    Si la consulta encara no ha acabat, get() bloqueja el fil que el crida fins que el resultat estiga disponible.

    get() amb temps màxim d'espera

    Podem evitar esperar indefinidament:

    String dades = resultat.get(
        2,
        TimeUnit.SECONDS
);

    En aquest cas esperarem com a màxim dos segons.

    Cal capturar TimeoutException:

    try {

    String dades = resultat.get(
            2,
            TimeUnit.SECONDS
    );

    System.out.println(dades);

} catch (TimeoutException e) {

    System.out.println(
            "La consulta està tardant massa"
    );
}

    cancel()

    També podem intentar cancel·lar una tasca que encara no ha acabat:

    boolean cancel·lada =
        resultat.cancel(true);

System.out.println(
        "Cancel·lada: " + cancel·lada
);

    Podem comprovar posteriorment l'estat:

    if (resultat.isCancelled()) {
    System.out.println(
            "La tasca ha sigut cancel·lada"
    );
}

    Important: cancel(true) demana la cancel·lació i pot interrompre el fil que executa la tasca. No significa que qualsevol operació externa es puga interrompre immediatament.

    Assignació de tasques a l'ExecutorService

    Una vegada coneixem Future, podem veure les diferents formes d'enviar tasques a un ExecutorService.

    execute()

    execute() s'utilitza quan només volem executar una tasca Runnable i no necessitem un resultat.

    Per exemple:

    ExecutorService executor =
        Executors.newFixedThreadPool(4);

Runnable tasca = () -> {

    try {

        String dades = SwapiClient.get(
                "https://swapi.dev/api/people/1/"
        );

        System.out.println(dades);

    } catch (Exception e) {

        System.out.println(
                "Error: " + e.getMessage()
        );
    }
};

executor.execute(tasca);

executor.shutdown();

    Amb execute() no obtenim cap Future.

    Per tant, si necessitem el resultat de la tasca, és més adequat utilitzar submit().

    submit()

    submit() permet enviar un Callable i obtindre un Future amb el resultat.

    Future<String> resultat =
        executor.submit(
                new ConsultaPersonatge(1)
        );

    Podem consultar posteriorment el resultat:

    System.out.println(
        resultat.get()
);

    Aquesta és probablement la forma que utilitzarem més sovint en els nostres exemples.

    invokeAll()

    Suposem que volem consultar diversos personatges.

    Podem crear una llista de tasques:

    List<Callable<String>> consultes =
        List.of(
                new ConsultaPersonatge(1),
                new ConsultaPersonatge(2),
                new ConsultaPersonatge(3),
                new ConsultaPersonatge(4)
        );

    I enviar-les totes a l'executor:

    List<Future<String>> resultats =
        executor.invokeAll(consultes);

    invokeAll() espera que totes les tasques hagen acabat i retorna una llista de Future en el mateix ordre que les tasques de la llista original.

    Podem recórrer els resultats:

    for (Future<String> resultat : resultats) {

    System.out.println(
            resultat.get()
    );
}

    Exemple complet

    import java.util.List;
import java.util.concurrent.Callable;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class ExempleInvokeAll {

    public static void main(String[] args)
            throws Exception {

        ExecutorService executor =
                Executors.newFixedThreadPool(4);

        List<Callable<String>> consultes =
                List.of(
                        new ConsultaPersonatge(1),
                        new ConsultaPersonatge(2),
                        new ConsultaPersonatge(3),
                        new ConsultaPersonatge(4)
                );

        List<Future<String>> resultats =
                executor.invokeAll(consultes);

        for (Future<String> resultat : resultats) {
            System.out.println(
                    resultat.get()
            );
        }

        executor.shutdown();
    }
}

    Això és especialment interessant perquè ara tenim quatre consultes que poden executar-se de manera concurrent.

    invokeAny()

    De vegades no ens interessen tots els resultats. Pot interessar-nos simplement el resultat de la primera tasca que finalitze correctament.

    Per exemple, podem enviar diverses consultes:

    List<Callable<String>> consultes =
        List.of(
                new ConsultaPersonatge(1),
                new ConsultaPersonatge(2),
                new ConsultaPersonatge(3),
                new ConsultaPersonatge(4)
        );

    I utilitzar:

    String primerResultat =
        executor.invokeAny(consultes);

    En aquest cas invokeAny() retorna el resultat d'una de les tasques que haja completat correctament.

    És important diferenciar-lo d'invokeAll():

    invokeAll()
    └── ens interessen TOTES les tasques

invokeAny()
    └── ens interessa el PRIMER resultat disponible

    Finalització del servei

    Quan ja no necessitem l'ExecutorService, hem de finalitzar-lo:

    executor.shutdown();

    shutdown() indica que no acceptarem més tasques, però permet que les tasques que ja estan en execució finalitzen.

    Si necessitem esperar que l'executor acabe:

    executor.shutdown();

executor.awaitTermination(
        10,
        TimeUnit.SECONDS
);

    Un patró habitual és:

    executor.shutdown();

if (!executor.awaitTermination(
        10,
        TimeUnit.SECONDS)) {

    executor.shutdownNow();
}

    Idea important: crear un ExecutorService implica també fer-se càrrec del seu cicle de vida. No hem d'oblidar-nos de finalitzar-lo.

    Exemple guiat: consultar diversos personatges

    Ara podem reunir els conceptes anteriors en un exemple més complet.

    Volem consultar informació de cinc personatges de SWAPI.

    import java.util.List;
import java.util.concurrent.*;

public class ExempleStarWarsConcurrent {

    public static void main(String[] args)
            throws Exception {

        ExecutorService executor =
                Executors.newFixedThreadPool(3);

        List<Callable<String>> tasques =
                List.of(
                        new ConsultaPersonatge(1),
                        new ConsultaPersonatge(2),
                        new ConsultaPersonatge(3),
                        new ConsultaPersonatge(4),
                        new ConsultaPersonatge(5)
                );

        List<Future<String>> resultats =
                executor.invokeAll(tasques);

        for (Future<String> resultat : resultats) {

            System.out.println(
                    resultat.get()
            );
        }

        executor.shutdown();
    }
}

    El pool té tres fils, però tenim cinc tasques:

    ExecutorService
     │
     ├── Fil 1 ──► Personatge 1
     ├── Fil 2 ──► Personatge 2
     └── Fil 3 ──► Personatge 3

Quan acaba una:
     │
     └── Fil disponible ──► Personatge 4

Quan acaba una:
     │
     └── Fil disponible ──► Personatge 5

    Això ens permet veure la diferència entre nombre de tasques i nombre de fils disponibles.

    Cues concurrents: BlockingQueue

    Abans de centrar-nos en les cues concurrents, hem de recordar què és una cua. Igual que les llistes i les piles, es tracta d'una estructura de dades complexa. La principal característica de les cues és que tenen una estructura FIFO (First In – First Out).

    La interfície BlockingQueue ofereix una cua segura per a l'accés concurrent. La característica més interessant és que les operacions poden quedar bloquejades:

    • put() espera si la cua està plena.
    • take() espera si la cua està buida.

    Això facilita la implementació del patró productor-consumidor.

    Exemple: productor-consumidor amb SWAPI

    Podem imaginar el següent problema:

    • els productors són responsables de consultar SWAPI;
    • els consumidors processen les dades rebudes;
    • la BlockingQueue comunica els dos grups de fils.
                  SWAPI
                ▲
                │
        ┌───────┴───────┐
        │               │
    Productor 1      Productor 2
        │               │
        └───────┬───────┘
                │
                ▼
        BlockingQueue
                │
        ┌───────┴───────┐
        │               │
    Consumidor 1    Consumidor 2
        │               │
        └───────┬───────┘
                ▼
             Resultat

    Podem crear una cua amb capacitat màxima de tres elements:

    BlockingQueue<String> cua =
        new ArrayBlockingQueue<>(3);

    Un productor pot afegir una dada:

    cua.put(dades);

    Mentre que un consumidor pot obtindre-la:

    String dades = cua.take();

    Exemple complet

    import java.util.concurrent.*;

public class ExempleBlockingQueue {

    public static void main(String[] args)
            throws InterruptedException {

        BlockingQueue<String> cua =
                new ArrayBlockingQueue<>(3);

        ExecutorService executor =
                Executors.newFixedThreadPool(4);

        // Productor
        executor.submit(() -> {

            try {

                for (int id = 1; id <= 5; id++) {

                    String dades =
                            SwapiClient.get(
                                "https://swapi.dev/api/people/"
                                + id + "/"
                            );

                    cua.put(dades);

                    System.out.println(
                        "Produït personatge " + id
                    );
                }

            } catch (Exception e) {

                Thread.currentThread().interrupt();
            }
        });

        // Consumidor
        executor.submit(() -> {

            try {

                for (int i = 0; i < 5; i++) {

                    String dades = cua.take();

                    System.out.println(
                        "Processant dades: "
                        + dades
                    );
                }

            } catch (InterruptedException e) {

                Thread.currentThread().interrupt();
            }
        });

        executor.shutdown();
    }
}

    En aquest exemple, la cua actua com a mecanisme de comunicació segur entre els fils.

    Observació: en una aplicació real caldria gestionar també de manera explícita el final de la producció i dels consumidors. L'objectiu d'aquest primer exemple és centrar-nos en el funcionament de put() i take().

    Implementacions de BlockingQueue

    Algunes implementacions habituals són:

    Classe Descripció
    ArrayBlockingQueue Cua de capacitat fixa basada en un array.
    LinkedBlockingQueue Cua basada en nodes enllaçats amb capacitat configurable.
    PriorityBlockingQueue Cua que permet consumir els elements segons un ordre de prioritat.
    DelayQueue Els elements només poden ser consumits quan ha passat el seu retard.
    SynchronousQueue No emmagatzema elements; cada inserció ha de coincidir amb un consumidor.

    Fils virtuals (Java 21 i posteriors)

    Des de Java 21, els fils virtuals formen part estable de la plataforma.

    Són especialment adequats per a aplicacions amb moltes tasques concurrents que passen bona part del temps esperant operacions d'entrada/eixida, com ara peticions HTTP.

    Les consultes a SWAPI són un bon exemple d'aquest tipus de tasca: el programa envia una petició, espera una resposta i després continua treballant.

    Podem crear un fil virtual per executar una consulta:

    Thread tasca = Thread.ofVirtual()
        .name("consulta-swapi")
        .start(() -> {

            try {

                String dades =
                        SwapiClient.get(
                            "https://swapi.dev/api/people/1/"
                        );

                System.out.println(dades);

            } catch (Exception e) {

                e.printStackTrace();
            }
        });

tasca.join();

    També podem crear un executor que assigne un fil virtual nou a cada tasca:

    try (ExecutorService executor =
        Executors.newVirtualThreadPerTaskExecutor()) {

    Future<String> resultat =
            executor.submit(
                new ConsultaPersonatge(1)
            );

    System.out.println(
            resultat.get()
    );
}

    En aquest cas no creem un pool de fils virtuals. El model és un fil virtual per tasca.

    Això resulta especialment interessant quan tenim moltes consultes independents:

    try (ExecutorService executor =
        Executors.newVirtualThreadPerTaskExecutor()) {

    for (int id = 1; id <= 20; id++) {

        int idPersonatge = id;

        executor.submit(() -> {

            try {

                String dades =
                        SwapiClient.get(
                            "https://swapi.dev/api/people/"
                            + idPersonatge + "/"
                        );

                System.out.println(
                    "Personatge " + idPersonatge
                    + " rebut"
                );

            } catch (Exception e) {

                System.out.println(
                    "Error en el personatge "
                    + idPersonatge
                );
            }
        });
    }
}

    Els fils virtuals no fan que una petició HTTP individual siga més ràpida. El seu avantatge és que permeten gestionar un nombre elevat de tasques concurrents amb esperes d'entrada/eixida.

    Compatibilitat: els exemples anteriors amb Thread, Runnable, Callable, Future i ExecutorService continuen sent vàlids en Java modern. Els fils virtuals amplien les possibilitats de concurrència i són especialment interessants per a tasques amb molta espera d'I/O.
