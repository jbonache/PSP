    4. La biblioteca java.util.concurrent

    Des dels inicis de Java la programació multifil ha sigut un dels aspectes fonamentals del llenguatge, amb la interfície Runnable i la classe Thread com a nucli.

    Des de Java 5, a més tenim a la nostra disposició la llibreria java.util.concurrent, que ofereix un conjunt de classes i interfícies orientades a gestionar la programació concurrent d'una forma més senzilla i òptima.

    En aquest apartat veurem una xicoteta introducció a aquesta llibreria. Concretament, veurem la interfície Callable, molt similar a Runnable, però que ens permet utilitzar valors de retorn.

    D'altra banda, l'API ExecutorService ens permetrà separar les tasques de creació de threads, la seua execució i la seua administració, encapsulant la funcionalitat i millorant el rendiment.

    I finalment, veurem la interfície BlockingQueue, que permet gestionar cues de manera que els seus accessos puguen ser bloquejants, la qual cosa ens serà de gran utilitat per a abordar els diferents problemes de sincronització i coordinació, com per exemple el del productor-consumidor, sense la necessitat d'utilitzar monitors.

    La llibreria java.util.concurrent

    La llibreria java.util.concurrent ofereix un conjunt molt ampli de classes i interfícies orientades a gestionar la programació concurrent d'una forma més senzilla i òptima.

    Entre totes elles, es troben l'API ExecutorService i la interfície Callable. La primera s'encarrega de separar les tasques de creació de threads, la seua execució i la seua administració, encapsulant la funcionalitat i millorant el rendiment, mentre que la interfície Callable ens resol el problema dels threads amb els valors de retorn.

    D'altra banda, la llibreria també presenta la interfície BlockingQueue i diverses classes que la implementen amb diferents estructures de dades, amb la característica comuna que els accessos poden arribar a ser bloquejants si la llista està buida o ha arribat al topall de la seua capacitat. Això ens serà de gran utilitat per a abordar diferents problemes de sincronització sense la necessitat d'utilitzar monitors en l'accés a objectes compartits.

    La interfície Callable

    La interfície Callable és una versió millorada de la interfície Runnable introduïda a Java 1.5, que permet retornar un valor en finalitzar la seua execució.

    Quan utilitzem la interfície Runnable, disposem d'un mètode run() que no accepta paràmetres ni retorna cap valor. Això no és un problema, sempre que no necessitem proporcionar ni obtindre dades del Thread. En canvi, quan hem necessitat proporcionar valors i obtindre resultats de l'execució d'un fil, hem optat per la comunicació mitjançant objectes compartits.

    Per part seua, la interfície genèrica Callable proporciona el mètode call(), que retorna un valor del tipus genèric. La sintaxi general d'una classe que implemente aquesta interfície serà la següent:

    public class claseCallable implements Callable<TipoGenerico> {

    // Constructor
    [public claseCallable(args){...}]

    // Método call
    public TipoGenerico call() throws InvalidParamaterException {
        ...
        return valor_retorno;
    }
}

    Com a principal diferència respecte a Runnable, podem veure com en la definició de la classe hem d'indicar ja un tipus de dades genèric, que serà el mateix que el del valor de retorn del mètode call, el qual, com veiem, utilitza ara un return per a retornar aquest valor.

    FutureTask

    Amb l'anterior definició, podríem utilitzar el mètode call directament:

    claseCallable miCallable=new claseCallable(args);
TipoGenerico valor=miCallable.call();

    Però amb això no estaríem executant el mètode de manera asíncrona. Una primera aproximació a això seria utilitzar directament la classe FutureTask, introduïda a Java 5 i que es pot utilitzar per a fer tasques asíncrones, ja que implementa la interfície Runnable, i per tant, pot llançar-se com un fil.

    La forma de fa això seria mitjançant la creació d'un objecte de tipus FutureTask, de manera genèrica, a partir de l'objecte creat de la classe Callable

    claseCallable miCallable=new claseCallable(args);
FutureTask<TipoGenerigo> miFutureTask=new FutureTask<TipoGenerico>(miCallable);

    Aquest tipus genèric serà el mateix que hàgem definit per a la nostra classe Callable. Atés que FutureTask implementa Runnable, podem crear ara un thread a partir d'aquesta classe i llançar-ho:

    Thread miThread=new Thread(miFutureTask);
miThread.start();

    Amb això el programa principal espera al fet que finalitzen els fils que ha generat. Una vegada haja finalitzat FutureTask, podrem accedir al valor retornat pel mètode call mitjançant el mètode get:

    TipoGenerico resultado=miFutureTask.get();

    Encara que, tal com hem vist és possible utilitzar la interfície Callable d'aquesta manera, el més habitual és utilitzar-la al costat de l'API ExecutorService, com veurem a continuació.

    L'API ExecutorService

    ExecutorService és una API de Java que ens permet simplificar l'execució de tasques asíncrones. Per a això, ens ofereix un conjunt de fils preparats per a assignar-los tasques.

    La forma més senzilla per a crear un ExecutorService és utilitzant la classe Executors, la qual proporciona diversos mètodes de factoria i utilitats per a la creació de múltiples APIs d'execució asíncrona.

    Per exemple, el mètode de factoria newFixedThreadPool, crea un servei d'execució asíncrona amb un conjunt de threads de longitud fixa. Per a crear un servei d'aquest tipus que pose a la nostra disposició fins a 10 fils d'execució faríem:

    ExecutorService servicio = Executors.newFixedThreadPool(10);

    A part d'aquest mètode, disposem de molts altres com newCachedThreadPool(), que genera els fils a mesura que es van necessitant. Podem consultar la llista de mètodes en la documentació oficial de la classe Executors.

    La manera de treballar amb aquesta API és relativament simple, ja que solament requereix d'instàncies d'objectes de tipus Runnable o Callable i ella s'encarrega de la resta de tasques.

    Així doncs, una vegada disposem del servei ExecutorService instanciado, tenim a la nostra disposició diferents mètodes per a assignar-li tasques. Però abans d'abordar aquests mètodes, veurem la interfície Future, per a entendre'ls millor.

    Future

    La interfície Future definida en el paquet java.utill.concurrent, representa el resultat d'una operació asíncrona. El valor de retorn, del tipus genèric indicat, no l'obtindrem de manera immediata, sinó que s'obtindrà en el moment en què finalitze l'execució de la tasca asíncrona. En aquest moment, l'objecte Future, tindrà disponible aquest valor de retorn.

    La interfície Future, proporcionarà perquè els mecanismes per a saber si ja es disposa del resultat, per a esperar a tindre resultat i per a consultar aquest resultat, així com per a cancel·lar la funció asíncrona si encara no ha acabat. Vegem en la següent taula els mètodes que ens proporciona aquesta interfície:

    Mètode Descripció
    boolean isDone() Retorna cert si la tasca ha acabat.
    TipoGenérico get() Retorna el valor retornat per la tasca, sempre que aquest estiga disponible. En cas de no estar disponible, espera al fet que ho estiga.
    TipoGenérico get(long t, TimeUnit u) Retorna el valor retornat per la tasca, sempre que aquest estiga disponible. En cas de no estar disponible, espera com a molt el temps t indicat en unitats de temps u.
    boolean cancel(boolean interrupcion) Intenta cancel·lar una tasca que està en execució. El booleà que li proporcionem indica si ha d'interrompre's per a cancel·lar la tasca.
    boolean isCancelled() Retorna cert si la tasca ha sigut cancel·lada abans de completar-se

    Assignació de tasques a l'executorService

    Ara que ja coneixem la interfície Future, examinarem diferents mètodes per a assignar tasques en el ExecutorService

    Mètode Descripció Ús
    void execute() Mètode heretat de la interfície Executor, que simplement executa la tasca indicada, peo sense la possibilitat d'obtindre el seu resultat o estat. ExecutorService s=...; \newline s.execute(tareaRunnable);
    Future<T> submit() Envia una tasca, bé de tipus Callable o Runnable al servei, retornant un tipus Future genèric T. ExecutorService s=...; \newline Future<T> resultado = s.submit(tarea);
    Future<T> invokeAny() Assigna una col·lecció de tasques al servei, i retorna el resultat de qualsevol d'elles. ExecutorService s=...;
    ...\newline Future<T> resultado = s.invokeAny(ListaTareas);
    List <Future<T>> InvokeAll() Assigna una col·lecció de tasques al servei, executant-les totes i retornant una llista de Futures amb els resultats ExecutorService s=...; \newline ... \newline List<Future<String>> resultados = s.invokeAll(ListaTareas);

    Finalització del servei

    Una vegada deixem d'utilitzar el servei i hàgem obtingut tots els resultats, utilitzarem el mètode shutdown per a finalitzar el servei:

    servicio.shutdown();

    Cues concurrents: BlockingQueue

    Abans de centrar-nos en les cues concurrents, hem de recordar què és una cua. Igual que les llistes i les piles, es tracta d'una estructura de dades complexa. La principal característica de les cues és que aquestes tenen una estructura FIFO (First In – First Out). El concepte és similar al de fer cua, en el supermercat, en el caixer del banc, on el primer que arriba és el primer a ser atés, i la resta de clients van incorporant-se al final de la cua.

    A Java aquest comportament l'ofereix la interfície Queue, que posseeix diverses classes que la implementen, com ArrayQueue, ArrayDeque o AbstractQueue, entre altres.

    D'altra banda, la interfície BlockingQueue ofereix un comportament similar, amb la diferència que a més aquest comportament ofereix mecanismes d'accés segurs en operacions concurrents (thread-safe), la qual cosa ens serà de gran utilitat a l'hora d'abordar problemes de sincronització, com el dels productors-consumidors. Mitjançant aquesta interfície, els fils productors hauran d'esperar a produir si la cua està plena, i els consumidors esperar a consumir mentre la cua estiga buida. Tot el comportament que generàvem mitjançant monitors en l'objecte compartit, ens el gestionarà ara la cua.

    Aquesta interfície, aporta dos mètodes a les cues: put i take, que serien els equivalents a add i remove, però amb la particularitat que les operacions es realitzen de manera segura.

    Vegem les diferents implementacions d'aquesta interfície en la següent taula:

    Classe Descripció
    ArrayBlockingQueue Implementa una cua mitjançant un array, per la qual cosa tindrà una longitud fixa. Les operacions de put i take asseguraran que no se sobreescriguen les entrades.
    LinkedBlockingQueue Implementa una cua mitjançant una llista enllaçada, on cada element de la llista és un node nou, amb el que, en principi podria créixer indefinidament (fins a arribar a Integer.MAX_VALUE). El seu constructor admet un enter per a especificar el nombre d'elements màxim que pot emmagatzemar. Les operacions de put i take asseguraran que no se sobreescriguen les entrades.
    PriorityBlockingQueue Implementa una cua mitjançant un heap binari basat en un array, la qual cosa permet consumir els elements en un ordre específic.
    DelayQueue Implementa una cua que conté elements que implementen la interfície Delayed. Els objectes que implementen aquesta interfície requereixen d'un retard (delay) per a operar sobre ells. Aquestes cues són útils per exemple quan un consumidor únicament pot consumir elements després d'un temps.
    LinkedTransferQueue Inclou el mètode transfer que permet a un productor esperar que es consumisca un item, de manera que els consumidors puguen manejar el flux de missatges produïts.
    SynchronousQueue Conté com a molt un element, de manera que representa una forma senzilla d'intercanviar dades entre dos fils.
    ConcurrentLinkedQueue Es tracta d'una cua no bloquejant, apta quan no necessitem que les operacions esperen. No implementa BlockingQueue.

    Fils virtuals (Java 21 i posteriors)

    Des de Java 21, els fils virtuals formen part estable de la plataforma. Continuen sent objectes Thread, però la JVM els planifica sobre un nombre reduït de fils del sistema operatiu. Són especialment adequats per a aplicacions amb moltes tasques concurrents que passen gran part del temps esperant operacions d'entrada/eixida, com ara servidors, peticions HTTP o consultes a bases de dades.

    Els fils virtuals no fan que una tasca calcule més ràpid: milloren l'escalabilitat i el rendiment global (throughput) quan hi ha moltes esperes bloquejants. Per a càrregues intensives de CPU continuen sent adequats els fils de plataforma i els executors dimensionats segons els nuclis disponibles.

    Thread tasca = Thread.ofVirtual().name("consulta").start(() -> {
    System.out.println("Executant en " + Thread.currentThread());
});
tasca.join();

    També podem crear un executor que assigne un fil virtual nou a cada tasca:

    try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<String> resultat = executor.submit(() -> operacioBloquejant());
    System.out.println(resultat.get());
}

    No hem de crear un pool de fils virtuals: el model recomanat és un fil virtual per tasca. Si cal limitar l'accés concurrent a un recurs escàs, usarem un mecanisme explícit com Semaphore.

    Compatibilitat: els exemples anteriors amb Thread, Runnable, Callable, Future i executors de fils de plataforma continuen sent vàlids. Els fils virtuals amplien l'API i no substitueixen la sincronització, la interrupció ni l'exclusió mútua.
