    4. Comunicacions UDP per a videojocs en xarxa

    Quan convé utilitzar UDP

    TCP ofereix un flux fiable i ordenat. Si es perd informació, el protocol la retransmet i no entrega els bytes posteriors fins que pot mantindre l'ordre. És adequat per a l'autenticació, l'entrada o l'eixida d'una partida, el xat, l'inventari o el resultat final.

    UDP envia datagrames independents. No garanteix que arriben, que ho facen una sola vegada ni que mantinguen l'ordre. A canvi, una pèrdua no retarda automàticament els datagrames posteriors. Açò el fa útil per a informació freqüent i ràpidament reemplaçable, com la posició, velocitat o orientació dels jugadors.

    En el nostre videojoc aplicarem aquesta divisió:

    Informació Transport Motiu
    Autenticació i assignació de l'identificador TCP No es pot perdre ni duplicar
    Entrada, eixida i canvi d'equip TCP Són esdeveniments puntuals i fiables
    Posicions i velocitats UDP Una instantània nova substitueix l'anterior
    Resultat de la partida TCP Ha d'arribar de manera íntegra

    Important

    UDP no és necessàriament «més ràpid» en totes les situacions. La diferència important per a un joc és que evita que la retransmissió d'un paquet antic bloquege l'estat més recent.

    Datagrames en Java

    Java proporciona DatagramSocket per a enviar i rebre datagrames i DatagramPacket per a representar cada missatge. A diferència de Socket, no obtenim fluxos d'entrada i eixida ni fem accept(): cada paquet conserva els límits del missatge i inclou l'adreça IP i el port d'origen.

    byte[] buffer = new byte[1200];
DatagramPacket packet = new DatagramPacket(buffer, buffer.length);
socket.receive(packet); // Bloqueja fins que arriba un datagrama.

String text = new String(packet.getData(), packet.getOffset(),
        packet.getLength(), StandardCharsets.UTF_8);
SocketAddress origin = packet.getSocketAddress();

    És important usar packet.getLength(): el búfer sol ser més gran que el missatge rebut. Per a enviar:

    byte[] data = message.getBytes(StandardCharsets.UTF_8);
DatagramPacket packet = new DatagramPacket(data, data.length, destination);
socket.send(packet);

    Protocol mínim de posicions

    UDP no defineix el format de les dades. Per a l'exemple didàctic utilitzarem text UTF-8 separat amb |:

    REG|jugador_1
POS|jugador_1|125.500|80.250
STATE|42|1780000000000|jugador_1,125.5,80.25;jugador_2,72.0,19.0;
    • REG associa temporalment un identificador amb l'adreça i el port UDP d'origen.
    • POS comunica al servidor l'última posició del jugador.
    • STATE és la instantània que el servidor envia a tots els clients registrats.
    • El número de seqüència permet descartar instantànies duplicades o antigues.
    • El temps del servidor facilita calcular interpolacions i diagnosticar latència.

    El text facilita l'aprenentatge i la depuració. En una versió avançada podem usar un format binari compacte, però sempre hem de definir-ne explícitament els tipus, l'ordre dels bytes, la versió i la longitud màxima.

    Grandària dels datagrames

    Encara que UDP permet datagrames grans, la fragmentació IP augmenta la probabilitat de perdre'ls. Com a criteri conservador per a Internet, l'exemple limita cada datagrama a 1.200 bytes. Si tots els jugadors no caben en una instantània, cal dividir-la en fragments identificats o, preferiblement, usar representacions binàries i enviar només les entitats rellevants per a cada client.

    Servidor Java que difon les posicions

    El codi complet està disponible en exemples/Apartat_4_UDP/java/UdpPositionServer.java. El servidor realitza dues tasques:

    1. El fil principal rep REG i POS i actualitza un ConcurrentHashMap.
    2. Un ScheduledExecutorService genera 20 instantànies per segon i les envia a tots els punts remots registrats.

    El mapa concurrent és necessari perquè el fil receptor i el planificador hi accedeixen simultàniament. Els clients que no envien cap paquet durant cinc segons s'eliminen; així no conservem indefinidament adreces que ja no participen en la partida.

    Per a compilar i executar l'exemple:

    cd exemples/Apartat_4_UDP/java
javac UdpPositionServer.java
java UdpPositionServer 9999

    Warning

    L'exemple identifica el jugador mitjançant text per a mantindre el protocol llegible, però això no és autenticació. En el projecte complet, el servidor TCP ha de crear un testimoni de sessió aleatori i el servidor UDP ha de verificar-lo abans d'acceptar actualitzacions. Tampoc s'ha de considerar vàlida qualsevol posició enviada pel client: el servidor ha d'aplicar límits de velocitat i les regles del joc.

    Client Godot 4

    Godot 4 ofereix PacketPeerUDP. El client complet es troba en exemples/Apartat_4_UDP/godot/udp_position_client.gd. El node:

    • obri un port UDP local;
    • configura el servidor com a destinació;
    • envia REG en iniciar-se i POS vint vegades per segon;
    • processa tots els datagrames pendents en cada fotograma;
    • descarta les instantànies amb una seqüència anterior a l'última aplicada;
    • emet snapshot_received amb un diccionari de posicions.

    Un controlador del joc pot connectar-se al senyal:

    func _on_udp_snapshot_received(_sequence: int, _time: int,
        players: Dictionary) -> void:
    for id in players:
        if id != $UdpPositionClient.player_id:
            update_remote_target(id, players[id])

    No convé assignar directament cada posició rebuda al node remot, perquè el moviment es veuria a salts. Guardarem almenys les dues últimes instantànies i mostrarem els jugadors amb un retard breu, interpolant entre totes dues. Per al jugador local podem aplicar predicció i, quan arribe l'estat autoritatiu, reconciliar les diferències de manera gradual.

    Pèrdua, duplicació i desordre

    El protocol de l'aplicació ha d'assumir que qualsevol datagrama pot:

    • no arribar;
    • arribar més d'una vegada;
    • arribar després d'un datagrama més nou;
    • ser falsificat o contindre dades incorrectes.

    Per a les instantànies de posició no retransmetem: quan en falta una, esperem la següent. El número de seqüència resol la duplicació i el desordre. Per als esdeveniments que sí necessiten confirmació, utilitzarem TCP, tal com hem establit en l'arquitectura del joc.

    El bucle de xarxa tampoc ha de dependre dels fotogrames renderitzats. El servidor usa una freqüència fixa de 20 Hz; el client pot renderitzar a 60 Hz interpolant. Augmentar indiscriminadament la freqüència consumeix amplada de banda i CPU, però no corregeix una connexió inestable.

    De l'exemple a una arquitectura real

    Una evolució raonable del projecte és:

    1. El client s'autentica per TCP i rep playerId, un testimoni UDP i el port de la partida.
    2. El client envia per UDP un missatge de registre signat amb aquest testimoni.
    3. El servidor associa la sessió TCP amb l'adreça UDP observada; no confia en una adreça enviada dins del missatge.
    4. El servidor simula l'estat autoritatiu del món a una freqüència fixa.
    5. Els clients envien entrades o posicions, segons el nivell de l'activitat.
    6. El servidor valida les dades i difon instantànies numerades.
    7. Godot interpola els jugadors remots i tracta el jugador local separadament.

    Note

    En xarxes domèstiques, el client pot estar darrere de NAT. Enviar primer REG crea temporalment el mapatge necessari perquè el servidor responga al punt d'origen observat. Per a una activitat en la mateixa xarxa local és suficient; desplegaments reals poden requerir mecanismes addicionals i protecció contra abús.

    Activitat proposada

    1. Executa el servidor Java i dos clients Godot amb identificadors diferents.
    2. Fes que cada client actualitze local_position amb la posició del seu personatge.
    3. Crea o actualitza els nodes dels jugadors remots quan arribe snapshot_received.
    4. Simula una pèrdua descartant aleatòriament un 10 % de les instantànies i comprova que el joc continua avançant.
    5. Implementa un búfer de dues instantànies i interpola el moviment remot.
    6. Mesura els bytes enviats per segon en augmentar el nombre de jugadors.
