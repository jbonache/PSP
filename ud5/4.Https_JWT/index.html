    4. Comunicacions segures. HTTPS i JWT.

    Creació d'una API REST Simple per https (Dir API_Simple_https)

    Per treballar amb https necessitem un certificat en el servidor, o podem treballar amb un certificat autosignat de proves (que evidentment no reconeixeran els navegadors).

    Pas 1. Creació dels certificats

    Per crear-nos un certificat anem a fer ús de l'eina OpenSSL. Per a això, llançarem l'ordre openssl de la següent forma:

    $ openssl req -x509 -sha256 -newkey rsa:2048 -keyout certificate.key -out certificate.crt -days 1024 -nodesGenerating a RSA private key

    Amb el qual s'iniciarà la generació de les claus, i se'ns faran algunes preguntes:

    .............................................+++++
.............+++++

-----

into your certificate request.

There are quite a few fields but you can leave some blank

    Amb això haurem generat els fitxers certificate.crt amb la clau pública i certificate.key amb la clau privada.

    Pas 2. Configurant express per servir https

    En primer lloc, afegim les dependències fs (filesystem, per accedir al sistema de fitxers i poder llegir les claus) i https.

    npm install fs

    npm install https

    Per crear ara el servidor HTTPS, importarem les noves biblioteques:

    // Accés al sistema de fitxers
import { readFileSync } from 'fs'; 
//  Accés al servei per https
import { createServer } from 'https';

    A més, per habilitar el servei per https, una vegada tenim instanciada app com a una aplicació Express farem:

    // Servidor HTTPS:
https.createServer({
    cert: fs.readFileSync('certificate.crt'),
    key: fs.readFileSync('certificate.key')
}, app).listen(8081, function() {
    console.log("Servidor https al port 8081");
});

    Com veiem, creem el servidor https amb els certificat generats, amb l'app i el posem a escoltar pel port 8081.

    Quan accedim al servidor, segurament se'ns mostrarà un misstge d'alerta com el següent, on se'ns avisa dels possibles riscs d'accedir a un lloc que no ofereix un certificat de confiança.

    Per continuar amb la petició, farem click en Advanced i en Accept the risk and continue.

    Autenticació a través de JSON Web Tokens (JWT)

    JSON Web Token (JWT) és un estàndard per l'intercanvi segur d'un token o testimoni d'autenticació en arquitectures client-servidor, com puga ser la web (serveis web inclosos).

    Aquest estàndard fa ús del format JSON per verificar la identitat o el rol de l'usuari al servidor. És a dir, un usuari (o una entitat) s'autentica al servidor amb un rol concret. El servidor genera un token que li envia al client, i el client fa ús d'aquest token en totes les comunicacions amb el servidor, per provar que té els drets corresponents al seu rol.

    JWT en la pràctica

    Per configurar JWT en el nostre projecte seguirem els següents passos:

    • Pas 1. Afegint biblioteques.

    En primer lloc, afegim les biblioteques JWT i CORS al nostre projecte. Aquesta segona servirà per acceptar peticions des de qualsevol origen.

    npm install jsonwebtoken

    npm install cors
    • Pas 2. Creant la configuració.

    Creem la carpeta config i el fitxer config/config.js, amb la configuració necessària per a l'autenticació:

    export const config = {
    key: process.env.JWT_SECRET,
    user: process.env.DEMO_USER,
    pass: process.env.DEMO_PASSWORD
};

    La clau de signatura i les credencials no s'han d'escriure al repositori. En desenvolupament podem carregar-les des d'un fitxer .env exclòs de Git (node --env-file=.env index.js) i, en producció, des del gestor de secrets de la plataforma. La clau ha de ser aleatòria i prou llarga. Si JWT_SECRET no existeix, l'aplicació ha de fallar en iniciar-se.

    Les variables DEMO_USER i DEMO_PASSWORD només mantenen senzill l'exemple docent. En una aplicació real les contrasenyes s'emmagatzemen amb un algorisme de hash específic per a contrasenyes, com Argon2id o bcrypt, amb sal i un cost adequat; mai en text pla.

    • Pas 3. Càrrega de biblioteques i configuració del servidor.

    Centrant-nos ja en el codi del servidor, el primer que farem serà importar les biblioteques necessàries i el fitxer de configuració:

    import cors from 'cors';

import { sign, verify } from 'jsonwebtoken';
import { key as _key, user, pass } from './config/config';

    Quan creem l'aplicació express, la configurem amb la clau de la configuració i també per utilitzar el middleware de CORS:

    const app = express();

app.set('key', config.key);
...
app.use(cors({ origin: 'https://client.exemple.test' }));

    Important

    CORS és una política dels navegadors i no un mecanisme d'autenticació. Les aplicacions mòbils natives i curl no estan sotmeses a aquesta política. En producció no convé usar cors() sense opcions: cal autoritzar només els orígens, mètodes i capçaleres que necessite el client.

    Podem llegir més informació a l'article Using CORS in Express.

    • Pas 4. Creant el middleware per a l'autenticació

    Ara ens cal definir una ruta que siga la que s'encarregue de fer l'autenticació. Al nostre exemple, hem afegit la ruta /auth, que serà la ruta a la que accedirem quan es faça el login. El tipus de petició a aquesta ruta serà POST, ja que necessitarem codificar els paràmetres d'usuari i contrasenya dins el body.

    Aquesta ruta comprovarà que l'usuari és correcte, i si és així, generarà el token per al client. Cal notar que aci hem definit usuari i contrasenya al fitxer config.js, però generalment açò serà un accés a la BD d'usuaris.

    Veiem el codi per a aquesta ruta:

    app.post('/auth', (req, res) => {
    // Contrastem amb usuari i contrasenya definits en config
    if (req.body.user === config.user && req.body.pass === config.pass) {
        const payload = { sub: config.user, role: 'admin' };
        const token = sign(payload, app.get('key'), {
            algorithm: 'HS256',
            expiresIn: '15m',
            issuer: 'psp-api',
            audience: 'psp-client'
        });

        res.status(200).json({
            // En la resposta retornem el token
            error: 0,
            message: 'Autenticació correcta',
            token: token
        });
    } else {
        res.status(401).json({
            error: 1,
            message: "Error en l'autenticació"
        })
    }
})

    Com veiem, el primer que fem és comprovar que les credencials de l'usuari. Si són correctes, fem el següent:

    • Declarem la constant payload (o càrrega útil) com a:
    const payload = {
    check: true
};

    Important

    Si desitgem que quan els usuaris s'autentifiquen al sistema se'ls assigne algun rol (administrador, usuari, etc.), podem afegir en aquesta càrrega útil la informació necessària. Aquesta informació s'afegirà al token, i per tant se'ns proporcionarà de manera codificada quan se'ns proporcione aquest. Per exemple, podríem fer:

    const payload = {
    check: true,
    role: "admin"
};
    • Creem el token, el signem amb un algorisme permés i li afegim una expiració curta. expiresIn: 1440 significa 1.440 segons, no 24 hores. Per a evitar ambigüitats usarem una cadena com '15m'. També incloem sub, iss i aud per identificar el subjecte, l'emissor i el destinatari.
    const token = sign(payload, app.get('key'), {
    algorithm: 'HS256',
    expiresIn: '15m',
    issuer: 'psp-api',
    audience: 'psp-client'
});
    • Una vegada generat el token, l'enviem juntament amb la resposta. En cas d'error d'autenticació, retornem un error en aquesta resposta. Observeu com podem fer ús del mètode status() per indicar-ne l'estat de la resposta i del mètode .json() que directament estableix el tipus de resposta com a application/json i fa el send:
        res.status(200).json({
            // En la resposta retornem el token
            error: 0,
            message: 'Autenticació correcta',
            token: token
        });
    } else {
        res.status(401).json({
            error: 1,
            message: "Error en l'autenticació"
        })

    Per tal de comprovar aquesta funcionalitat amb curl haurem d'incorporar-li el paràmetre -k, per tal de poder acceptar certificats que no siguen de confiança. Açò ho hem ara perquè sabem que el certificat del servidor l'hem creat nosaltres, però no és una opció segura per accedir a altres llocs.

     curl -k -d "user=usuari&pass=contrasenya" -X POST https://127.0.0.1:8081/auth

    Si l'autenticació falla ens retornaria:

    {"error":1,"message":"Error en l'autenticació"}

    I si aquesta té èxit:

    Com voreu, el token conté dos punts al seu contingut. Aquests punts divideixen aquest en tres parts, que es corresponen a l'esquema següent:

    token = encodeBase64Url(header) + '.' + encodeBase64Url(payload) + '.' + encodeBase64Url(signature)
    • Pas 5. Creació de rutes protegides.

    Fins ara el que hem fet ha estat autentificar l'usuari i proporcionar-li un testimoni (token) amb cert temps de vida. Aquest testimoni serà proporcionat en cada petició que requerisca de determinats permisos o rols. Per exemple, per consultar informació sobre els contactes no es necessitarà cap permís especial (i per tant no caldria cap mecanisme d'autenticació), però per afegir nous contactes sí que podríem requerir que l'usuari tingué el rol d'administrador.

    I aci és on entra de nou el component Router, de manera que aquelles rutes que puguen ser susceptibles de requerir autenticació, o rutes protegides, hauran de passar prèviament per l'autenticació.

    Veiem-ho al codi. En primer lloc, definim un nou router per a l'autenticació:

    const routerAuth = express.Router();

    El format estàndard per a enviar el token és Authorization: Bearer <token>. A més de comprovar la signatura i l'expiració, fixarem explícitament l'algorisme, l'emissor i l'audiència esperats.

    En cas que s'haja proveït un token, però l'autenticació no siga correcta, en aquest callback se'ns proporcionarà un error com a prime argument. En aquest cas, retornarem en la resposta l'error 401, Token invàlida. Si no hi ha cap error, l'usuari esetarà autenticat correctament, i el que farem serà passar al pròxim middleware mitjançant la funció next()-

    routerAuth.use((req, res, next) => {
    const authorization = req.get('authorization');
    const token = authorization?.startsWith('Bearer ')
        ? authorization.slice(7)
        : null;

    if (token) {
        verify(token, app.get('key'), {
            algorithms: ['HS256'],
            issuer: 'psp-api',
            audience: 'psp-client'
        }, (err, decoded) => {
            if (err) {
                return res.status(401).json({
                    error: 1,
                    message: 'Token invàlid'
                });
            } else {
                req.decoded = decoded;
                // Si tot va bé, passem al següent middleware
                next();
            }
        });
    } else {
        res.status(401).json({
            error: 1,
            message: 'Token no proporcionat.'
        });
    }
});

    Important

    Si estem fent ús d'autorització basada en rols, quan verifiquem el token, obtindrem en l'argument decoded el contingut que havíem afegit al payload, de manera que amb req.decoded.role (o el nom que hajam posat), podrem accedir al rol Per exemple, si es requereixen permisos d'administrador, es podría fer:

    verify(token, app.get('key'), (err, decoded) => {
    if (err) {...});
    } else { // Comprovació del rol
        if (req.decoded.role!="admin") 
            return res.status(401).json({
                error: 1,
                message: 'No es tenen privilegis'
            });
        else{        
            next();
        }
    }
});

    Per tal de comprovar-ne el funcionament, i una vegada ens hem autentificat i disposem d'un token, realitzarem una petició amb curl on afegirem a la capçalera el tipus de dades que s'acceptaran com a resposta (-H "Accept: application/json") i el token d'accés (-H "Authorization: Bearer eyJh...Dp89_s"), així com la resta de dades necessàries (-d) i el tipus de petició (-X):

    curl -H "Accept: application/json" -H "Authorization: Bearer eyJh...Dp89_s" -X PUT -d "nombre=user2&email=user2@hmail.com" -k https://127.0.0.1:8081/api/users

    La resposta del servidor, al nostre cas serà:

    {"status":"ok"}

    JWT en clients Flutter/Dart

    Per tal d'incorporar l'autenticació basada en token JWT en les nostres aplicacions amb Dart/Flutter, bàsicament haurem de mantindre la gestió dels tokens. Això es traduirà en:

    • Realitzar l'autenticació en el servidor proporcionant-li les credencials
    • Recollir el token que ens envia el servidor i emmagatzemar-lo internament
    • Enviar el token en les diferents peticions que requeridquen autenticació.

    Aplicant això al nostre exemple de gestió d'usuaris, que tindreu disponible en el fitxer client_users_app_jwt.zip, realitzarem les següents modificacions.

    Passos previs

    Abans que res, i només en entorn de desenvolupament, mai en producció, anem a configurar l'aplicació per a que accepte certificats del servidor autosignats. Per a això, caldrà crear una nova classe derivada de HttpOverrides i configurar amb ella l'aplicació. El codi corresponent serà:

    // HttpOverrides està en dart:io
import 'dart:io';

...

// Estenem la classe HttpOverrides per tal de
// confiar en certificats autosignats.
class MyHttpOverrides extends HttpOverrides {
  @override
  HttpClient createHttpClient(SecurityContext? context) {
    return super.createHttpClient(context)
      ..badCertificateCallback =
          (X509Certificate cert, String host, int port) => true;
  }
}

void main() {
  // Establim l'HTTP Overrides a nivell global
  // per confiar en els certificats autosignats.
  // NO UTILITZAR EN PRODUCCIÓ!!
  HttpOverrides.global = MyHttpOverrides();

  runApp(const MyApp());
}

    Amb açò, ja evitarem l'excepció:

    Unhandled Exception: HandshakeException: Handshake error in client (OS Error: E/flutter ( 2566): CERTIFICATE_VERIFY_FAILED: self signed certificate

    Realitzar l'autenticació en el servidor per proporcionar-li les credencials

    En l'exemple hem fet una vista nova LoginForm que recull el nom de l'usuari i la contrasenya. Quan l'usuari ingressa aquests paràmetres i fa clic al botó de login, s'invoca un nou mètode de la nostra biblioteca http_requests.dart, el mètode login, proporcionant-li l'usuari i la contrasenya.

    En aquest fitxer, hem definit prèviament la variable privada token, i hem definit tres variables més per emmagatzemar l'adreça del servidor (per a que siga més fàcil de modificar), tant per a HTTP com per a HTTPS:

    // Definim el token
String _token = "";

// Afegim el server com a variable
// Localhost en Genymotion és 10.0.3.2, en Android 10.0.2.2
String _server = "10.0.3.2";
String _httpServer = "http://$_server:8080";
String _httpsServer = "https://$_server:8081";

    Veiem ara la funció login: 

    Future<bool> login({required String username, required String password}) async {
  ...
}

    Com veiem, aquesta rep el nom de l'usuari i la contrasenya, i retorna un Future que es resoldrà a un valor lògic, indicant si l'autenticació ha estat realitzada amb exit o no.

    Per enviar la petició al servidor, crearem una petició POST a la ruta /auth, proporcionant-li en el cos els paràmetres user i pass (que hem definit al servidor), amb els valors que se'ns proporcionen com a arguments.

    String url = '$_httpsServer/auth';

http.Response response = await http.post(
  Uri.parse(url),
  headers: <String, String>{
    'Content-Type': 'application/json; charset=UTF-8',
  },
  body: jsonEncode(<String, String>{'user': username, 'pass': password}),
);

    Recollir el token que ens envia el servidor i emmagatzemar-lo internament

    Quan el servidor ens responga, comprovarem que l'autenticació és correcta, i si tot és correcte, ens guardem el token i resolem el Future a true. Veiem el codi complet:

    Future<bool> login({required String username, required String password}) async {
  String url = '$_httpsServer/auth';
  // Petició POST per a l'autenticació

  http.Response response = await http.post(
    Uri.parse(url),
    headers: <String, String>{
      'Content-Type': 'application/json; charset=UTF-8',
    },
    body: jsonEncode(<String, String>{'user': username, 'pass': password}),
  );

  debugPrint(response.statusCode.toString());

  if (response.statusCode == HttpStatus.ok) {
    String body = utf8.decode(response.bodyBytes);
    final result = jsonDecode(body);

    if (result["error"] == 0) {
        // Si no hi ha error ens guardem el token
        _token = result["token"];
    } else {
      // En cas contrari, llancem una excepció
      throw Exception(
          'Error en el servidor: ${result["error"]}, ${result["message"]}');
    }
    // I resolem em Future a True
    return true;
  } else {
    // Si no carrega, llancem una excepció
    throw Exception('No s\'ha pogut connectar');
  }
}

    Amb açò, al formulari d'autenticació, quan fem click al botó per enviar el formulari, invocarem la funció login. Quan la resposta es resolga (responsa.then), si aquesta té èxit, el que farem serà llançar una nova ruta amb la vista ja de l'aplicació (que ara hem anomenat MainAppView):

    var resposta = login(
    username: controladorNom.text,
    password: controladorPass.text);

resposta.then(

);

    Enviar el token en les diferents peticions que requeridquen autenticació.

    Com que ja tenim el token emmagatzemat, ara per relitzar les operacions que requereixen d'autenticació (com la d'afegir usuaris), el que faran és afegir aquest token en la seua capçalera. Veiem com fer-ho a la funció d'afegir usuaris:

    Future afigUsuari({required String nom, required String email}) async {
  // Configurem la URL per HTTPS
  String url = '$_httpsServer/api/users';

  http.Response response = await http.put(
    Uri.parse(url),
    headers: <String, String>{
      'Content-Type': 'application/json; charset=UTF-8',
      // Afegim a la capçalera el token
      'Authorization': 'Bearer $_token',
    },
    body: jsonEncode(<String, String>{'nombre': nom, 'email': email}),
  );


  if (response.statusCode == HttpStatus.ok) {
    String body = utf8.decode(response.bodyBytes);
    final result = jsonDecode(body);

    return result["data"];
  } else {
    // Si no carrega, llancem una excepció
    throw Exception('No s\'ha pogut connectar');
  }
}

    Si comparem el codi amb el què hi havia anteriorment, el canvi principal ha estat en què hem afegit a la capçalera 'Authorization': 'Bearer $_token',.
