    2. Express. Adreçament, programari intermedi i API REST

    Adreçament i mètodes de ruta

    L'adreçament en Express consisteix en la definició de punts finals d'aplicació o endpoints (URI) i com es respon a les sol·licituds de client.

    Els mètodes de ruta es corresponen amb els mètodes HTTP i s'adjunten a una instància d'Express. Entre altres, Express admet get, post, put, patch, delete, head i options; en els exemples utilitzarem principalment els cinc primers.

    A part d'aquests mètodes, existeix un mètode d'adreçament especial: app.all(), que no es correspon amb cap mètode HTTP i que s'utilitza per a carregar funcions de middleware per a tots els mètodes de sol·licitud.

    D'altra banda, disposem de les vies d'accés de ruta, que es combinana amb els mètode de sol·licitud per a definir aquests punts finals sobre els quals realitzar les sol·licituds. Així doncs:

    $$Punto.de.acceso.de.la.aplicació = Método.de.ruta + Vía.de.acceso.de.ruta$$

    Aquestes vies d'accés poden ser tant cadenes literals com patrons o expressions regulars

    Alguns exemples de vies d'accés de ruta que podem usar són els següents (extrets de la documentació oficial d'Express):

    • Via d'accés de ruta per a les sol·licituds a la ruta arrel, mitjançant el mètode de ruta GET
    app.get('/', function (req, res) {
  res.send('root');
});
    • Via d'accés que coincideix amb les sol·licituds al recurs /about, mitjançant el mètode GET
    app.get('/about', function (req, res) {
  res.send('about');
});
    • Express 5 ja no interpreta ?, + o * com els patrons de cadena d'Express 4. Per a fer coincidir acd i abcd, podem emprar una expressió regular de JavaScript:
    app.get(/^\/ab?cd$/, function(req, res) {
  res.send('Patró ab?cd');
});
    • Via d'accés que coincideix amb el patró ab+cd, on + indica una o més repeticions del caràcter que el precedeix, per la qual cosa coincidirà amb abcd, abbcd:
    app.get(/^\/ab+cd$/, function(req, res) {
  res.send('ab+cd');
});
    • Via d'accés que coincideix amb el patró ab.*cd, on .* indica qualsevol seqüència de caràcters:
    app.get(/^\/ab.*cd$/, function(req, res) {
  res.send('ab.*cd');
});

    Note

    En la documentació oficial d'Express sobre adreçament pots trobar més exemples de rutes, també amb expressions regulars.

    Manejadores de rutes i Middleware

    Per a gestionar les respostes a les diferents peticions utilitzem funcions de callback, que actuen com middleware. Quan el PATH i el mètode sol·licitats coincideixen amb una ruta, s'executa el callback definit en la instància d'Express per a aquesta ruta.

    Així doncs, amb el mètode app.get(path, MiddleWare), el que fem és instal·lar el Middleware en l'a plicación perquè només s'execute quan arriben sol·licituds HTTP de tipus GET path. Si arriba una petició a la mateixa ruta amb un altre mètode (PUT, POST, DELETE) o el propi GET però amb un altre PATH, es passa al següent middleware, sense executar aquest.

    Per a instal·lar un Middleware (MW) utilitzarem bé el mètode use(MW), o bé amb el mètode (get, post, etc.). Com ja hauràs deduït, els middleware s'invoquen en l'ordre d'instal·lació.

    Note

    La principal diferència entre usar use i un mètode HTTP és que use respon a qualsevol mètode i a qualsevol ruta.

    L'atenció a una sol·licitud HTTP finalitzarà quan s'invoque a res.send(...), que envia la resposta i finalitza l'execució, de manera que quan s'atén una petició que envia una resposta, els següents middleware ja no s'executaran.

    Paràmetres

    Aquests callbacks o middleware reben diversos paràmetres. Els dos primers són:

    • req: Un objecte Javascript amb els paràmetres sobre la sol·licitud HTTP, com el mètode usat o el path entre altres.
    • res: Un objecte Javascript per a configurar la resposta HTTP, com el tipus MIME del recurs, o el codi d'estat.

    Vegem-ho amb el següent exemple. Si afegim el següent Middleware:

    app.get("/info", function(req, res) {

    // Parámetros de la petición
    let metodo = req.method;
    let ruta = req.path;
    let host = req.get("host"); // Alias de req.header("host");

    // Configuración de la respuesta
    let tipo = "text/plain";
    let estado = 200;

    // Uso de template string para la salida
    let salida = `Método: ${metodo} 
Ruta: ${ruta}
Host: ${host}
`;

    res.type(tipo);
    res.status(estado);

    res.send(salida);
});

app.get('*', function(req, res) {
    console.log("Callback general");
    res.send(`Lo siento, no encuentro ${req.url}`);
});

    Com veiem, hem instal·lat un middleware per a la ruta /info, que ens retorna paràmetres relatius a la petició, com el mètode, la ruta, o l'Host (aquest últim utilitzant el mètode get de l'objecte req que és un àlies del mètode header). En la resposta, a més es configura el tipus com a text pla, i amb el codi d'estat 200.

    Note

    Per a realitzar les peticions al nostre servei, podem utilitzar directament el navegador, o aplicacions tipus Postman que ens permeten una major configuració de les peticions.

    APIs REST amb Express

    Una API és un conjunt de definicions i protocols que permeten la interacció entre sistemes per a obtindre dades o executar certes funcionalitats, de manera que el sistema comprenga la sol·licitud i la complisca.

    A principis del segle XXI, no existia cap estándard sobre disseny d'APIs, i aquestes s'implementaven usant altres protocols com SOAP, pesats i complexos. Va ser llavors quan va sorgir, de la mà de Roy Fielding la transferència d'estat representacional, RE*presentational State T*ransfer (REST)

    Fielding va proposar una sèrie de principis d'arquitectura per a les aplicacions web escalables, conegudes com a Arquitectura Orientada a Recursos. Aquests principis són:

    • Client-servidor: Client i servidor han de ser entitats independents, de manera que únicament es comuniquen mitjançant sol·licituds .HTTP,
    • Sense estat (stateless): La comunicació entre el client i el servidor ha de ser sense estat, això és, sense que s'emmagatzema o compartisca informació entre peticions. Cada petició serà independent, i contindrà únicament la informació per al seu processament.
    • Direccionalibidad/Identificador únic (URI): Tot recurs ha de tindre un identificador irrepetible, de manera que no existisquen dos o més recursos amb el mateix identificador en la xarxa, i a més, han de mantindre una jerarquia lògica.
    • Ús correcte d'HTTP: Respectant els verbs (mètodes GET, POST, PUT, PATCH, DELETE) i codis d'estat per a cada operació.

    A més es proposa l'ús de recursos en format obert, com a HTML, XML, JSON, etc

    Note

    En l'article Fonaments de l'arquitectura REST disposes de més informació interessant sobre aquests principis i altres recomanacions interessants per al desenvolupament d'APIS REST.

    Rutes en Express i APIs REST

    La manera de definir rutes en Express està dissenyada per a facilitar la creació d'APIS REST.

    Aquestes rutes estan formades per segments separats per /, que poden ser de dos tipus:

    • Segments literals: compostos per text amb caràcters permesos en URLs, combinats amb els caràcters especials *, ? i +.
    • Paràmetres: Variables que es proporcionen a través de la URL.

    Paràmetres del path

    Un client HTTP pot enviar paràmetres a través de les URL (conegudes com a URL pesades o fat URL). Aquests paràmetres es poden identificar en Express en la definició de les rutes que accepta utilitzant el caràcter :, i accedint a elles a través de l'objecte req.params

    Per exemple, un servei de tire molt simple seria:

    app.get("/echo/:texto", function(req, res) {
    res.send(req.params.texto);
});

    Com veiem, rep un paràmetre text, al qual accedim amb req.params.texto, i ho retornem en la resposta. Amb això, si el client realitza la petició http://127.0.0.1:8080/echo/Hola obté Hola com a resposta

    Altres exemples de rutes més complexes però útils podrien ser:

    • /usuario/:id, Per a obtindre un usuari pel seu id (req.params.id),
    • /series/:idSerie/temporadas/:temporada/capitulos/:capitulo, on idSerie (req.params.idSerie), temporada (req.params.temporada) i capitulo (req.params.capitulo) serien els paràmetres per a referenciar un capítol dins d'una temporada d'una sèrie.

    A Express 5 ha canviat la sintaxi de les rutes. Els paràmetres opcionals ja no s'indiquen amb ?; s'han d'envoltar amb claus. Per exemple:

    • /usuarios{/:id} respondrà tant a /usuarios/123 com a /usuarios.

    Express 5 ja no admet expressions regulars incrustades en una cadena de ruta com /usuario/:id(\\d+). La ruta captura el valor i el codi l'ha de validar; per exemple, podem comprovar req.params.id amb una expressió regular i retornar 400 Bad Request si no és vàlid. També podem passar una expressió regular completa com a ruta, però no hi obtindrem paràmetres amb nom.

    D'altra banda, un segment també pot incloure diversos paràmetres separats per "-" o per ".", per exemple: /:from-:to o /:file.:extension

    Note

    Si desitgem també atendre a queries de tipus GET amb l'aspecte: /recurso?parámetro=valor, podem utilitzar l'objecte query de la petició de la següent manera:

    app.get("/usuario", function(req, res) {
    res.send(req.query.id);
});

    Amb això, podem realitzar peticions tipus http://127.0.0.1:8080/usuario?id=Pepe

    Composició i execució de Middlewares

    Una aplicació Express consisteix en la instal·lació de middlewares associats a determinades rutes i mètodes, de manera que quan rep una petició HTTP, avalua els middlewares en l'ordre d'instal·lació, de manera que s'invoca al primer que concorde amb el mètode i la ruta de la sol·licitud.

    Recordem que un middleware no és més que una funció que, fins ara, rebia dos paràmetres: req i res. Podem completar aquesta funció amb un tercer argument next:

    function(req, res, next) { /* Cos del middleware */ }

    Aquest tercer paràmetre serveix per a indicar a l'aplicació Express que continue avaluant els middlewares següents quan finalitze l'execució del middleware on s'invoca.

    Si un middleware no invoca next(), com en els middlewares vistos fins ara, ha d'enviar una resposta mitjançant res.send(), res.json(), res.end() o un mètode equivalent. En cas contrari, el client quedarà esperant una resposta.

    Un altre aspecte a tindre en compte és que en Javascript tots els objectes són tractats mitjançant referències, per la qual cosa els objectes req i res poden tractar-se com a objectes persistents en una mateixa transacció. D'aquesta manera, un middleware pot crear o processar propietats de req i res per a les seues middlewares posteriors, activats mitjançant la funció next()

    A més, disposem dels objectes app.locals i res.locals, que podem utilitzar per a passar dades entre middlewares de l'aplicació, concretament:

    • app.locals permet crear propietats persistents a l'aplicació (entre diferents transacciones HTTP).
    • res.locals permet crear propietats dins de la mateixa transacció HTTP, que desapareixen quan acabe.

    L'enfocament que ofrecce Express amb els middlewares permet una programació seqüencial i modular, però amb els avantatges de la programació funcional i basada en esdeveniments de Javascript.

    Vegem un xicotet exemple consistent en un comptador de visites per al nostre lloc.

    Instal·larem els següents middlewares en el nostre servidor, just abans d'instal·lar el middleware Static:

    // Contador de visitas
app.use(function(req, res, next) {
    if ('visits' in app.locals) {
        app.locals.visits++;
    } else app.locals.visits = 0;

    next();
});

app.get("/visits/show", function(req, res) {
    res.send(`Número de visitas: ${app.locals.visits}`);
});

app.get("/visits/reset", function(req, res) {
    app.locals.visits = 0;
    res.send("Contador de visitas reseteado");
});

    Com veiem, hem instal·lat tres middlewares nous:

    • El primer coincidirà amb qualsevol petició (ja que es defineix amb use), i internament té el següent funcionament: Comprova si l'objecte app.locals posseeix un camp visits. En cas que no ho continga, ho crearà, inicialitzant-ho a 0. Si aquest existeix, el que farà serà incrementar-ho en una unitat. Finalment, invoca a next(), perquè continue examinant els següents middlewares.

    • El segon, coincideix amb la petició GET servidor:puerto/visits/show",i el que fa és retornar en res un text amb el valor d'aquest comptador.

    • El tercer, coincideix amb la petició GET servidor:puerto/visits/reset", I el que fa és reinicialitzar aquest comptador de visites, retornant un missatge amb de confirmació.

    Com veiem, l'efecte del primer middleware és incrementa el comptador en cada visita al servidor, independentment del recurs que se sol·licite, ja que coincideix amb qualsevol petició. Recordem que app.locals és un objecte persistent en l'aplicació Express, per la qual cosa el seu valor no s'eliminarà després de cada transacció HTTP.

    Important

    Què passaria si el primer middleware s'haguera instal·lat al final?

    Observem la importància de l'ordre d'instal·lació dels middlewares, ja que una vegada que una petició coincidisca amb un mètode i una ruta executa el middleware associat, i finalitzaria l'execució sempre que no s'invoque a next

    Middlewares d'error

    Els errors o excepcions es gestionaran mitjançant middlewares d'error.

    Un middleware d'error es defineix amb un paràmetre inicial addicional (err):

    function(err, req, res, next) { /* Cos del middleware d'error */ }

    I s'invoca mitjançant la funció next() proporcionant-li el codi d'error: next(err)

    La diferència principal enre next() i next(err) és que el primer indica a Express que continue avaluant els següents middlewares, i la segona que avalue els següents middlewares d'error.

    Per a instal·lar un middleware d'error, ho farem exactament igual que la resta de middleware, associant-los a rutes i mètodes

    Cal destacar que dins d'un middleware d'error, també podem invocar a next() per a indicar que es continuen examinant la resta de middlewares o a next(err), per a indicar que es continuen examinant els middlewares d'error. Per exemple, si es produeix una excepció que se soluciona en un middleware d'error, amb next() podem seguir el flux d'anàlisi normal de middlewares.

    Important

    Recordem que per a cada transacció HTTP, hem d'assegurar-nos de retornar una resposta al client, ja siga en un middleware comú o en un d'error.

    La manera d'estructurar els middlewares serà similar a com estructurem el nostre codi mitjançant blocs d'excepcions try-catch

    Vegem un exemple per a un servidor estàtic que únicament acceptarà peticions GET:

    import express from 'express';
import path from 'path';
import url from 'url';

const __filename = url.fileURLToPath(
    import.meta.url);
const __dirname = path.dirname(__filename);

const app = express();

// Middleware 1
app.use('*', function(req, res, next) {
    if (req.method.toLowerCase() !== "get") {
        res.locals.status = "405";
        next(new Error("405. Method Not Allowed"));
    }
    next();
})

// Middleware 2 (Static)
app.use(express.static(__dirname + '/public'));

// Middleware 3
app.get("*", function(req, res, next) {
    res.locals.status = "404";
    next(new Error("404 Not Found"));
});

// Middleware de error
app.use(function(err, req, res, next) {
    res.status(res.locals.status);
    res.send(err.toString());
});

    En aquest codi, el primer middleware que instal·lem comprova mitjançant req.method que el mètode que se sol·licita és GET. En cas contrari, invocarà al middleware d'error, proporcionant-li un error amb el text 405. Method not allowed. A més, utilitzarà l'objecte res.locals per a emmagatzemar el codi d'error. Si es tracta d'un mètode GET, continuarà amb l'eXecuió.

    El segon middleware, Static, atén les sol·licituds de recursos estàtics, situats en la carpeta public. Si el recurs existeix, se serveix, i es finalitza l'execució.

    En cas que no existisca cap recurs, es llançarà el tercer middleware, que casa amb qualsevol ruta, i que estableix el codi d'error "404 Not Found" per a invocar al middleware d'error.

    Finalment, ens trobem amb aquest middleware d'error, que establirà el codi d'error i retornarà el missatge d'error al client.

    peticions POST i PUT

    A nivell de funcionalitat, una petició POST és igual a una petició GET. La diferència es troba en la manera d'enviar els paràmetres. El mètode GET envia els paràmetres usant la pròpia URL, mentre que POST els envia de manera oculta en el propi cos de la petició.

    Per a enviar paràmetres en una petició GET podíem fer-ho:

    • Bé des de la mateixa ruta: 
    curl -X GET http://127.0.0.1:8080/api/users

curl -X GET http://127.0.0.1:8080/api/users/pepe

    I en aquest cas obtindríem els arguments en el servidor definint la ruta '/api/users{/:nombre}' i accedint als paràmetres amb req.params.nombre

    • Bé proporcionant-los com a consultes de tipus GET, incorporant lso arguments en la URL:
    curl -X GET http://127.0.0.1:8080/api/users?nombre=paco

    La diferència és que ara obtindríem les dades mitjançant req.query.nombre

    Petciones POST

    El mètode POST s'utilitza per a enviar una entitat a un recurs específic, podent modificar l'estat del servidor (per exemple, enviar una imatge.)

    Per a suportar peticions POST, s'utilitza el mètode post(path, MW), de la mateixa manera que utilitzàvem get, i fem ús de req i res dins del Middleware per a accedir als paràmetres de la petició i generar la resposta.

    A diferència dels paràmetres de consulta d'un GET, les dades principals d'un POST solen anar en el cos de la petició. Express incorpora els parsers necessaris per a JSON i formularis.

    Una vegada definida l'aplicació Express, activem els formats que acceptarem:

    app.use(express.json({ limit: '100kb' }));
app.use(express.urlencoded({ extended: false }));

    Amb això haurem inicialitzat el middleware, i ens quedarà crear les rutes que utilitzarem per a atendre les peticions POST:

    app.post('/api/users', function(req, res) {

    let nombre = req.body.nombre || null;

    res.status(200);
    let response = getUser(nombre);
    if (!response) response = { "status": "error", "msg": "User not Found" };

    res.send(response);

});

    Fixeu-vos, que per a accedir al cos de la petició fem ús de req.body, i el component corresponent a la clau que busquem (nom).

    Per a realitzar mediant curl una petició POST farem:

    curl -d nombre=pepe -X POST http://127.0.0.1:8080/api/users

    De manera que amb -d afegim al cos de la petició el paràmetre nombre amb valor pepe per a la consulta

    Peticions PUT

    Si el que es desitja és afegir un recurs, podem utilitzar peticions de tipus PUT. Aquest tipus de peticions s'usaran de la mateixa manera que les peticions POST, això és, proporcionem els paràmetros en el cos de la funció, i els obtenim mitjançant req.body:

    app.put('/api/users', function(req, res) {

    // Para peticiones POST debemos 
    let nombre = req.body.nombre || null;
    let email = req.body.email || null;

    console.log(nombre);
    console.log(email);

    let response;

    if (nombre && email) {
        addUser(nombre, email);
        response = { "status": "ok" }
    } else response = { "status": "error", "errorMsg": "Undefined Data" };

    res.send(response);

});
